# Vitris client workspace prototype

## Prospect preview and signup

The local Vitris installation also explicitly enables **Prospects & onboarding**, a separate optional module. Choose **Prepare a prospect**, enter their business/contact and test-site URL, and configure up to ten questions for that client. Questions support short/long answers, phone numbers and website links, required flags, prefilled answers, and Business or Website stages. Blank test-site URLs use a visibly illustrative sample layout. Hosted links retain their own access settings; this portal does not make an external website private. No page authoring or deployment is performed.

**Onboarding templates** provides Professional services, Home & construction, and Hospitality & experiences starters. Customize a starter or create your own template with a name, business category, welcome message, signup headline/introduction, questions and payment-step setting. Saved templates can be edited, duplicated and archived. The question editor supports ordering and optional hints. **Save these questions as a template** in the prospect form strips all prefilled client answers. Applying a template copies its definition into a prospect snapshot; later edits/archive never change existing invitations. Revision checks reject stale template saves and selection. Every template query and write is scoped to the exact installation, site and admin origin.

Each saved and starter template has **Preview client flow**. It opens the actual shared client screens in an owner-authorized full-page view before any prospect is assigned. Use **Preview step** to inspect welcome, configured signup stages, payment (when requested) and completion; **Desktop / Phone**, **Use sample answers**, and **Reset preview** help review layout and validation. **Back to templates** returns to the library. Only the existing authenticated workspace GET loads definitions. Preview answers exist in browser memory only; password entry is disabled and no prospect, invitation, account, draft, session, email or payment is created. Refresh resets the rehearsal. Missing or archived templates show an unavailable state. Ordinary, disabled and unauthorized admins cannot load this optional preview.

`tests/template-flow-preview.test.ts` verifies the shared-stage walkthrough, absence of API writes and record creation, saved/starter definitions, optional-stage omission, phone width, reset/reload, unavailable templates and access gates. Preview verification screenshots are under ignored `artifacts/template-flow-preview/`.

While creating or editing a template, choose **Preview changes** to rehearse the exact unsaved definition in that same full-page experience. **Back to editing** or browser Back restores the editor draft; example answers and **Reset preview** never change it. This also works before a new template has a name or has been saved. Only **Save template** persists changes. Drafts stay in memory in the signed-in onboarding workspace; reloading, signing out, or leaving the module discards them. Reopening an unavailable draft preview explains how to return to templates. `tests/template-draft-preview.test.ts` covers draft isolation, return navigation, edited copy/questions/steps, save-after-preview and mobile layout. Screenshots are under ignored `artifacts/template-draft-preview/`.

Preparing saves a draft account. Open **Manage → Generate setup link → Try prospect experience** to see the invitation. The prospect sees their test-site preview before signing up. **Complete signup** opens a full-page mobile journey through Your business, Your website (when configured), Your account and optional Payment setup. Signup and payment use no customer dialogs. Progress, inline errors, phone/URL keyboards and back/continue actions are accessible; mobile inputs use 16px text. Non-secret answers are saved when continuing or going back. A prospect-scoped HttpOnly invitation cookie permits refresh/resume until the invitation expires or is replaced/revoked. Neither raw link tokens nor passwords enter browser storage or draft records. Account creation validates the original snapshot and consumes the invitation atomically. Returning clients use `/prospect` to sign in. Their restricted dashboard contains only their preview, submitted details, website feedback and payment status, without staff permissions or portfolio analytics.

The separate full-page payment step is clearly labeled **Local preview**. It accepts no card details, makes no Stripe calls, charges nothing, and records only a sample completion. Clients can postpone it and open their dashboard with payment still pending. Account activation and payment completion have separate statuses. Owner feedback/status updates appear after **Refresh**. **Revoke access** invalidates the invitation and all prospect sessions immediately. Setup links expire after 24 hours; replacement invalidates the previous link. No emails are sent.

The explicit runtime import is `@tryvitris/website-admin-harness/prototypes/client-onboarding`. Register `clientOnboardingPrototype` and enable `client-onboarding` only in the intended isolated local manifest. Its owner-only permissions are `prospects:read` and `prospects:write`. Optional migrations `0010_client_onboarding_prototype.sql` and `0011_onboarding_templates.sql` live under `prototypes/client-onboarding/migrations/`, outside ordinary installation migrations. Migration 0011 adds template records and config/draft columns without changing existing prospects. Records, password verifiers, hashed invitation tokens and hashed HttpOnly prospect sessions are scoped by site, installation and exact admin origin. No core staff user is created or changed by the module. It rejects production mode and connected remote-backend installations.

The preview launcher stores private local D1 state under ignored `.vitris/portfolio-state/` and its stable prospect password pepper in `.vitris/portfolio-runtime.json`. Keep both together; a missing key on an existing state directory blocks startup instead of silently replacing credentials. A local migration ledger applies only missing migrations. The one-time private record snapshot preserves the prior preview's prospect, owner and session records when moving into persistent local storage. Normal test fixtures remain isolated and ephemeral. This persistence is local to this workstation, not a production account rollout.

Production work must deliberately provision each client's installation/hostname and account, connect the reviewed account lifecycle and email delivery, pair it with only that client's website/billing grant, and use Stripe-hosted payment-method setup with provider-confirmed completion. Do not promote this local portal authentication or sample payment state into production. The existing optional Stripe billing module remains separate and unchanged.

Acceptance tests are `tests/client-onboarding.test.ts`, `tests/client-onboarding-ui.test.ts`, `tests/onboarding-templates.test.ts` and `tests/onboarding-templates-ui.test.ts`. They cover scoped/disabled/unauthorized access, template snapshot/revision rules, migration from the previous schema, missing-key recovery guards, persistence across restarts, invitation replacement/expiry/reuse, concurrent activation, draft integrity/resume, required/typed fields, password login, no staff elevation, feedback, revocation and desktop/mobile flows. External packed-runtime acceptance includes the optional module and both migrations.

The workspace also supports an authenticated live-analytics mode. A private `.vitris/portfolio-connections.json` selects the owner-approved websites and references their existing server read credentials by file/key. The adapter verifies the backend identity and read scope, and requests only status and analytics. The browser receives validated analytics, never credentials or credential file paths. Real records are labeled **Live analytics**; update requests, previews, release checks and publishing remain simulations.

With private live connections configured, `npm run vitris:preview` disables **Open local demo** and creates no predictable test accounts or sessions. It writes an expiring, one-use owner sign-in URL to ignored `.vitris/portfolio-owner.json`. Run **`npm run vitris:signin`** in another terminal to open a fresh private owner sign-in in the default browser, then choose **Continue to workspace**. The link opens Prospects & onboarding; Clients is available in the sidebar. `npm run vitris:signin -- file-only` renews the private link for a native app handoff without opening an external browser. Renewal uses a secret-authenticated local IPC channel, preserves test records and sessions, and adds no HTTP development-login endpoint. The plain preview URL explains this private sign-in instead of showing an unusable email form. Lost/expired links can be renewed repeatedly while the process remains running. The default installation without this private configuration still follows the synthetic walkthrough below. Missing/rejected connections show an unavailable state and contribute no synthetic or stale figures. Comparisons require complete matching periods; new collection has no historical traffic to reconstruct.

Live connections are local to this workstation. The dashboard process must remain running to serve requests. Restarting it reopens the private local database and creates fresh owner sign-in links without clearing prospects, templates, client credentials or saved progress. This does not replace either website's production admin or enable real publishing.

Each live website shows a verified **Tracking started** date in the portfolio and connection details. Its Analytics history card distinguishes that activation date from the first nonzero activity in the retrieved records, and explains when the selected range begins before collection. Activation dates display in Eastern time; daily record dates are labeled UTC. Empty padded days never establish a start date. Missing activation evidence displays **Not verified**, and an unavailable source does not imply zero historical visits. Configure the optional `trackingStartedAt` as a canonical ISO UTC timestamp in the private website entry; the date remains the same when switching reporting windows.

Without private live connections, run `npm run vitris:preview`, open **http://127.0.0.1:4393/#client-portfolio** and choose **Open local demo**. The preview is a separate local installation, so normal `npm run dev` and existing customer admins are unchanged. Requests, receipts, templates and progress remain in private local storage when the process stops.

The optional Clients module includes a portfolio of three example clients and four websites, client filtering and search, 14/30-day analytics, detailed website analytics, connection diagnostics, and a persistent simulated update/release workflow. One website has unavailable analytics and contributes no numbers to portfolio totals. All fixture domains use `example.test`.

Try a complete flow:

1. Open a website or select **Request an update**. Enter a title and request.
2. Select **Start demo agent**, then **Build demo preview**. Alternatively, simulate a build failure and retry it.
3. Open **Review & publish**. Inspect the illustrative preview and candidate, acknowledge the simulation, and select **Queue simulated publish**.
4. Select **Run simulated publish**, then choose **Published simulations** to see the receipt. Refresh to verify it persists.
5. Toggle the demo runner offline to see jobs wait for it to reconnect. Cancel an open change to stop that simulation.

The preview layout does not implement the request. Agent execution, release checks, candidate preparation, and publication are all simulated. There is no production deployment, external fetch, AI invocation, customer email, or secret configuration in this module. Its timestamps show local display time; the analytics series uses UTC. Sum of daily visitors is not a count of unique people across sites or days.

## Optional installation boundary

`examples/vitris` explicitly registers `client-portfolio` and `client-onboarding` and enables them in its local manifest. The shared UI loads the dedicated chunks only when the modules are enabled and authorized (or an explicit prospect invitation route is opened). The ordinary initializer and existing manifests do not enable them. Core Overview, Leads, Analytics, Settings, Users and access, and Activity retain their existing scope.

The packaged runtime exposes `@tryvitris/website-admin-harness/prototypes/client-portfolio` as an explicit optional import. The additive migration lives under `prototypes/client-portfolio/migrations/0009_client_portfolio_prototype.sql`, outside the ordinary migration directory. Apply it only to an isolated local prototype database after the core schema. It adds a site-scoped snapshot table without modifying users or existing records. The preview helper performs only those local setup steps and provides no deploy command.

The module requires local mode, an exact loopback admin origin, no remote backend connection, and the installation owner. The capabilities `clients:read`, `client-changes:request`, and `client-releases:publish` are owner-only. Browser action bodies cannot supply user roles or installation scope. All changes use the stored revision, atomic compare-and-swap updates, scoped IDs, and candidate-specific publication approval. Duplicate requests/publication retries retain the same change or receipt. Only one active candidate per website can enter the simulated agent flow.

## Validation and next integration

Run `npm run check`. Dedicated acceptance tests are `tests/client-portfolio.test.ts` and `tests/client-portfolio-ui.test.ts`. The package smoke test also loads this module and its migration from an installed tarball outside the workspace. Browser checks save desktop/mobile and review screenshots to ignored `artifacts/vitris-prototype/`.

Production implementation requires dedicated read-only analytics grants per website, scoped team memberships, a paired operator bridge, active-agent handoff, real preview/check evidence, approved candidate verification at upload, and actual deployment reconciliation. Those are separate from this local prototype. Preserve each website's forms, exact origins, users, records, grants, and release policy. Do not enable this prototype against a production backend or deploy/migrate a shared backend to demonstrate it.

To disable the variant, remove its trusted registration and manifest ID. Keep the additive local tables for recovery; disabled modules have no enabled routes or background jobs. Stopping the preview pauses it and preserves private local records. No automatic deletion or reset runs during upgrades or sign-in renewal.
