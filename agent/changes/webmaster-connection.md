# Reusable webmaster connection

Add an explicitly enabled built-in `webmaster` connection under Settings. The owning client chooses the organization, whether it also provides billing, named existing non-owner accounts, and agreed operational capabilities. Ownership, user administration, seller billing and client billing are excluded from webmaster grants. No new bindings or services are needed.

Use additive core migration `0011_webmaster_connections.sql` for installation/site/exact-origin-scoped connections, persistent member restrictions, and immutable activity attribution. Existing accounts, origins, forms and records remain unchanged. Removing members, disconnecting, or disabling the module must fail closed for previously managed accounts rather than restoring their underlying role. Existing `account-billing` remains independently enabled and authorized; disconnect never calls a subscription cancellation API.

Expose authenticated GET/POST `/api/modules/webmaster`, owner-only configuration with revision checks, and owner-only POST `/api/modules/webmaster/disconnect`. Show relationship, scope, optional billing provider identity, and explicit subscription warning in Settings. Keep the existing Your billing experience for subscriptions, invoices, payments and hosted payment management.

Verify scoped/disabled/revoked access, optional leads and billing, cross-installation isolation, malformed grants, migration preservation, attribution, desktop/mobile controls, and packed external consumption. Run `npm run check`. Release diff: runtime/contracts/UI/docs plus this additive migration; no cloud writes, deployment, secrets or remote migration. Before a separately authorized installation rollout, back up its owning D1 database, review its source/module diff, apply locally first and test real account permissions. Code rollback does not cancel subscriptions; retain restriction rows and disable managed users before rolling back to a runtime that predates these restrictions.
