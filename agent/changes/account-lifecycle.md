# Owner setup, invitations, verification and password recovery

Build opt-in account lifecycle routes in the standalone admin, with the shared default sender accounts@tryvitris.com. Existing accounts, password verifiers, exact origins, local-demo restrictions and website connections remain intact. No production migration, deployment or customer email send is part of this build.

Add migration 0009 for installation/origin-scoped owner enrollment, verified account profiles, purpose-bound one-use action digests, encrypted email outbox and atomic completion guards. Only a provisioned empty installation can enroll its designated first owner. Team invitations require verified ownership, a fresh password check and the owner-only access:write permission; invitations cannot grant ownership or reactivate an existing account.

Token completion, credential changes, verification, session revocation and audit records must commit together. Guard against reused/expired/cross-installation tokens, role/revocation races, concurrent owner claims, changed credentials and link scanners. Existing password verifiers stay supported; new credentials use PBKDF2-SHA256 at 100,000 iterations with a per-account salt and the existing server-side HMAC pepper. Reset requests never reveal account existence; reset completion revokes sessions and old login links and queues a confirmation notice.

Cloudflare Email Service remains the provider. A verified sender readiness flag, restricted AUTH_EMAIL binding and separate encryption key gate delivery. Encrypt queued messages/tokens at rest, deliver outside request timing through waitUntil/cron, and expose delivery status without exposing token links. Keep live delivery and local capture evidence distinct. No SMS integration.

Include branded UI for setup, verification, invitation acceptance, forgot/reset password and owner team invitations/resend/cancel, plus CLI owner provisioning and generated setup instructions. Validate migration from the previous schema, authorization and races in workerd/D1, browser desktop/mobile flows, and installation from packed packages outside the workspace. Run npm run check. Preserve concurrent unrelated scheduling/portfolio work.

Runtime compatibility: preserve the existing PBKDF2-SHA256 100,000-iteration, 1,536-bit output plus HMAC-SHA256 installation pepper. Cloudflare imposes a 100,000-iteration per-derivation cap (workerd issue 1346); the six output blocks preserve the existing work factor. Existing 256-bit and 1,536-bit credentials remain accepted. No custom KDF or new authentication vendor.

## Installation diff

- Replace the runtime package and copied UI assets with the verified build. The new declaration file is included in the packed public runtime. No change to website backend grants, form IDs, theme configuration, business records or customer assets.
- Add migration `0009_account_lifecycle.sql`. It creates `auth_owner_setup`, `auth_profiles`, `auth_actions`, `auth_action_completions` and `auth_mail_outbox`, indexes and atomic action guards. Initial migration does not rewrite users, password credentials or sessions. Subsequent identity changes invalidate sessions/tokens; explicit reset changes that user's credential. Existing migrations are untouched.
- New write permission: `access:write`, owner only. New public routes are `/api/auth/setup/request`, `/api/auth/password/reset/request`, `/api/auth/action` and `/api/auth/action/complete`. Signed-in users can request verification at `/api/auth/verification/request`; only verified owners can create/resend/cancel `/api/access/invitations`. All mutation routes use exact-host and same-origin checks, input bounds and scoped rate limits.
- New installation defaults: `AUTH_ACCOUNTS_ENABLED=1`, `PASSWORD_LOGIN=1`, `AUTH_EMAIL_READY=0`, shared `AUTH_FROM=accounts@tryvitris.com`, restricted `AUTH_EMAIL` sender binding and a one-minute cron. Local scaffolds retain explicit loopback-only demo mode without any email binding or account-feature flag.
- Installation secrets: preserve `PASSWORD_PEPPER`; add separate `AUTH_EMAIL_ENCRYPTION_KEY`. Keep readiness off until the sender is approved. Do not import credentials, overwrite the owner, change hostname, or provision sender/DNS/backend resources as a package upgrade side effect.
- First owner SQL contains only the installation/origin/email designation and is ignored by Git. It is rejected by the database if any account exists. Existing installations use their existing owner plus email verification. The build does not generate passwords, print action links, send customer email, migrate live D1, publish npm packages or deploy.
- Recovery: take a D1 backup first; preserve the password pepper and email key. Disable the account feature to stop lifecycle routes/delivery if needed. Keep the additive schema and existing accounts; do not roll the database backward. Replace pending links explicitly when rotating the mail key. See the packaged account runbook.
- Existing Pages deployments require a reviewed wrapper that forwards `waitUntil` and a reliable queue-drain scheduling strategy; this Worker package does not silently convert or deploy them. The sole previously identified Perrotta installation remains untouched by this build.
