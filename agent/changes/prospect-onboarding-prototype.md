# Optional prospect onboarding prototype

Add `client-onboarding` as a separate, explicitly enabled local Vitris variant alongside Clients. The owner prepares a prospect's business/contact, an assigned HTTPS test-site link (or an illustrative local preview), and a welcome message. Preparing a record grants no staff or website-admin access. An explicit action creates a 24-hour, one-use setup link; local preview exposes it for copying/testing and sends no email. The prospect confirms their name and chooses a password, then sees only their assigned preview and can leave feedback. Returning prospects can sign in; owner revocation immediately blocks existing sessions. Show Draft, Awaiting setup, Expired, Active, and Revoked distinctly.

User clarification: preview is visible before signup. Completing signup opens the prospect's own scoped client dashboard with remaining-information fields configured per client, preserved prefilled values, and an optional Stripe payment-method step. The local prototype simulates a payment-method completion explicitly and never accepts card numbers or changes real billing. Account activation/profile completion and payment completion remain separate statuses. A hosted external test page retains its existing access policy. The default illustrative preview is visibly a sample, not a generated client website.

Production payment-method collection should extend the existing opt-in Stripe adapter with hosted Checkout `mode=setup` (SetupIntent) and verified webhook reconciliation. No arbitrary Stripe link, raw card entry, payment status from redirects, implicit subscription/charge, or account creation in a real Stripe account. Reference: https://docs.stripe.com/payments/save-and-reuse?platform=checkout . The existing billing module is concurrent work and remains unchanged in this slice.

Keep staff lifecycle/invitations unchanged. Use existing password derivation with a separate ephemeral local pepper, installation/site/origin-scoped prospect records, hashed action/session tokens, atomic setup completion, Origin checks on public POST hooks, and a separate HttpOnly prospect cookie. Never create a harness staff user or disclose owner analytics/client records to prospects. This local module requires explicit local mode, an exact loopback HTTP origin, no remote backend, owner-only `prospects:read` / `prospects:write`, and its own optional migration outside ordinary core migrations.

No production deployment, shared database migration, remote content changes, or recipient notifications. Production scope will reuse the reviewed account lifecycle/mail infrastructure with deliberate tenant provisioning and invitation delivery; the local portal is an experience prototype, not a production authentication rollout. Hosted preview links keep their own access policy; the portal does not privatize an external website.

Validate local workerd/D1 scopes, disabled/unauthorized access, link expiry/replacement/reuse, atomic acceptance, password login, feedback/revocation and no staff account creation. Exercise owner and prospect flows at desktop/mobile sizes, install the packed runtime outside the workspace, and run `npm run check`. Keep the local dashboard running for the user's testing.
