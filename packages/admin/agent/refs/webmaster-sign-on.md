# Named webmaster sign-on

Version 1.3.0 adds optional sign-on for one explicitly configured Vitris owner. It is independent of organization reporting and billing. No human login is granted by an analytics credential. No account is created, promoted or selected by email matching. A client owner explicitly maps the pinned Vitris subject to an existing named local account; the runtime resolves that account's current approved permissions on every request.

## Installation diff

Read WORKFLOW.md and refs/webmaster.md. Preserve accounts, verifiers, exact origins, existing reporting grants, billing and mail. Apply optional `modules/webmaster/migrations/0013_webmaster_signon.sql` deliberately after core 0011 to the owning D1, following a backup and local migration rehearsal. It adds broker flow/lease tables, client flow/grant/session tables, and an organization-revocation trigger. Keep trigger bodies intact when applying SQL. No runtime DDL, seeding or automatic migrations occur. Existing installations without sign-on keep their normal login.

Broker manifest: `"webmasterSignOn":{"mode":"broker"}`. Configure one exact `WEBMASTER_SSO_SUBJECT_ID`, referring to the existing active owner user ID, and the installation's private P-256 `WEBMASTER_PAIRING_SIGNING_KEY`. Other users, including other owners, cannot start sign-on. Do not auto-select the first owner at runtime or derive this ID from an email address. The private Vitris Websites module supplies reviewed saved client identities to the public `/signon` SDK's `startWebmasterSignOn(context,target)` helper; it discovers capabilities through bounded public-address checks and never accepts arbitrary browser callback URLs.

Client manifest (public key and IDs are explicit reviewed installation configuration):

```json
{"webmasterSignOn":{"mode":"client","broker":{"installationId":"APPROVED_BROKER","siteId":"APPROVED_SITE","adminOrigin":"https://admin.approved-domain.com"},"subjectId":"APPROVED_OWNER_USER_ID","organizationId":"APPROVED_WEBMASTER_ORGANIZATION","publicKey":{"kty":"EC","crv":"P-256","x":"PINNED_PUBLIC_X","y":"PINNED_PUBLIC_Y"}}}
```

Enable the built-in `webmaster` module and connect the actual organization. Install a separate 32-byte lowercase hex `WEBMASTER_SSO_KEY` secret on this client to encrypt server-held PKCE verifiers, pending assertions and leases, bound to installation/site/origin/record. Keep a secure recovery copy. Existing website backend credentials, reporting keys, billing secrets and hostnames stay unchanged. Pin the real broker's public key through the reviewed deployment diff; never download and silently repin a key at login. Broker signing-key rotation requires an explicit client pin update and new owner account approval. Do not enable fixture transports or demo login in production.

## Browser and server contract v1

Contracts export `signOnBase`, `signOnPolicy`, pinned identities, signed assertion/status types and configuration. Base: `/api/webmaster-sso/v1`. The broker is a server-side session authority, not a shared cookie domain. Each admin continues to use its own HttpOnly host-only session cookie. Only register/exchange/introspect are exempt from browser Origin checking; all browser writes require exact same Origin and JSON. Owner approval/revocation requires the normal active client owner session, independently of Vitris.

1. An authenticated, explicitly configured owner clicks Open site admin. POST to the private Websites module creates a five-minute broker flow bound to the original session digest and exact existing client installation/site/admin origin. No existing reporting token is sent.
2. The client landing page immediately removes fragment parameters from browser history and POSTs begin. A registered client flow uses an HttpOnly SameSite=Strict browser cookie and a server-held random PKCE S256 verifier. Its fixed, pinned broker receives the audience/state/challenge; an arbitrary URL cannot receive a secret.
3. The browser returns to the broker's authorization page. A same-origin POST must carry the original authenticated owner session, original state and flow. It produces a single-use code valid for 60 seconds, returned only in the exact client origin's fragment. Codes do not enter query logs/referrers or audits.
4. The client checks its own browser flow cookie and exchanges the code server-to-server with PKCE and exact audience. The broker atomically consumes the code, verifies the original owner session is still active, and returns a P-256-signed assertion with a dedicated opaque session lease and bounded expiration (at most eight hours and never beyond the original session).
5. The client verifies its pinned key, exact broker/client/subject/flow identity and expiration. If a named-account mapping is missing or revoked, a client owner signs in normally, selects an existing approved account, reviews its current role, and explicitly approves. This does not change that account's role/permissions. The client then creates a linked local session and records named person/organization attribution.
6. Every authenticated request using this linked session makes a fresh bounded, redirect-free broker introspection. The signed response binds a fresh nonce, lease hash, exact audience, configured subject and current source-session validity. There is no positive cache or offline grace. Outage, bad signature, wrong audience, disabled sign-on, account/membership revocation, source-session expiration or Vitris logout denies access. Ordinary independently authenticated client sessions are unaffected. Visible harness UIs recheck every five seconds and on focus/visibility, clearing the signed-in view when access ends; hidden tabs check when visible again. Data already displayed cannot be retroactively erased.

Public client GET capabilities returns only version, client/broker identity, single subject, public-key ID and fixed begin path. Broker POST register/authorize/exchange/introspect and client POST begin/complete/approval/approve/revoke use strict bounded JSON. Client owner GET grants lists safe mappings; no verifier, assertion, code, raw lease or session cookie is returned. Error responses use 400/403 invalid fields/browser/audience, 401 lost authentication, 404 disabled, 409 changed/consumed intent, 410 expired flow and 503 missing reviewed schema/key or unavailable peer. Lost one-use authorization/exchange/completion responses require starting a fresh launch from Vitris; no code is replayed or silently upgraded into a reusable login credential.

## Revocation and recovery

Vitris sign-out deletes its existing owner session(s); every linked client checks those original digests and rejects further requests immediately after logout. It does not rely on logout delivery to each client. Client sign-out retains its ordinary local behavior. Removing a person stops their human access while retaining the organization's reporting grant. Revoking a named sign-in mapping invalidates its sessions without changing reporting or billing. Disconnecting/changing the whole organization permanently revokes its named mappings and sessions through the additive database trigger, including under older writers. Reconnecting the organization cannot revive an old session; explicit account approval is required again.

Do not delete human-session restriction records as a rollback step. Disabling sign-on in the current runtime still rejects its old linked sessions. A runtime predating this feature cannot enforce linked-session introspection: before such rollback, explicitly delete linked session rows from ordinary `sessions` using the scoped `webmaster_sso_sessions` records, or revoke them through the reviewed upgrade runtime. Keep the additive tables and keys. Database-backup restoration is a separately reviewed recovery because it replaces legitimate subsequent changes. No sign-on action cancels billing, modifies subscriptions or grants payment-management permissions.

Ship broker and client against the same contract. Publication, new client migrations/secrets and live activation are separate explicit installation actions.
