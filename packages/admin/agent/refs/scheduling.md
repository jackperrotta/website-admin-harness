# Optional scheduling foundation

Scheduling is an unreleased built-in module, explicitly enabled by `modules: ["scheduling"]` after reviewing local packages and additive migration `0004_scheduling.sql`. `createAdmin` registers it; do not scaffold another module with that ID. Keep existing entry points, manifests, accounts and business records intact. Do not enable it or migrate a customer database during unrelated setup.

The dedicated Scheduling interface provides day/week/agenda views, Services, Team, Availability and Booking settings, with appointment creation, approval/status changes, cancellation, staff rescheduling and history. It uses authenticated `/api/modules/scheduling` routes and requires no website leads/analytics backend connection or a website leads binding. Google/Microsoft OAuth, busy-time import, appointment export, conflict review and `.ics` files are implemented; read `calendar-sync.md` before enabling them. Apply additive migration 0005 and configure business-owned apps, encryption and cron explicitly. Enabled connections receive real writes, including test appointments. The standard website component and public API now support explicitly published test bookings; read `public-booking.md` before enabling them and apply new migration 0006. Customer emails and appointment-scoped cancellation/rescheduling links are implemented; read `customer-notifications.md` before enabling them. Capture is the local default; sending needs explicit provider setup and designated test recipients. Production booking remains unavailable. Captured jobs are synthetic outputs, not successful external writes. Calendar sync remains required for launch.

Use shared DTOs and strict parsers from `@tryvitris/website-admin-contracts/scheduling`. Configuration is a bounded site-scoped aggregate with an optimistic global revision. Appointments have their own revision and immutable service/price/approval snapshots. Use current global and appointment revisions on writes and idempotency keys for appointment commands. Never calculate authority, durations, prices or confirmed status from a browser declaration.

Owner and administrator accounts can configure scheduling. Other accounts require explicit configuration grants. Own-scoped grants resolve provider resources through trusted account assignments; they must never expand to other providers. Availability edits cannot replace another provider's hours or expose the complete configuration. The command guard rechecks current account status, permissions and resource scope inside the transaction.

Use the filtered `/workspace` response for the UI. Do not grant provider clients full configuration or the account directory to render their own schedule. Preserve drafts and their original revision on conflicts. Appointment searches return current terms; reschedule searches authorize the existing appointment and preserve its snapshot. Keep local times tied to the location timezone, offer explicit offsets during repeated hours, and reject nonexistent times. Browser acceptance uses real local D1 with synthetic records; install Chromium with `npx playwright install chromium` before `npm run check`.

All mutations retain canonical-host, authenticated-session and exact admin Origin checks. Test mode is the only booking mode supported by this foundation. Preserve the site-constrained database triggers and transaction boundary around command receipts, appointments, reservations, jobs and history. Do not replace overlap checks with an application-level read followed by an insert. Preserve existing bookings when availability changes or new booking is disabled.

Apply schema changes only through a new reviewed migration; never edit earlier migrations. Verify from packed packages outside the workspace and run `npm run check`. A production release requires separate reviewed provisioning/migrations, calendar provider onboarding, backup/recovery, deployment and live checks. Never send test messages or write calendar events to customer accounts without explicit authorization.
