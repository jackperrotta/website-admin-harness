# Owner setup and account email

Each business has its own accounts, database and exact admin origin. The default shared sender for new installations is `accounts@tryvitris.com`; the business name and canonical admin link identify which workspace sent the email. This is a configuration default, not evidence that the domain or inbox has been provisioned. Use Cloudflare Email Service only. No SMS or additional paid provider is introduced.

## New installation

1. Scaffold with `vitris-admin init ... --owner-email OWNER_EMAIL`, or use `--owner-email` with the reviewed `setup --plan` / `setup --apply` flow. For an existing empty scaffold, run `vitris-admin owner-setup --dir INSTALLATION --email OWNER_EMAIL`. The command writes ignored `.vitris/owner-setup.sql`; it makes no cloud calls and sends no email. Review the exact recipient, installation ID and HTTPS origin.
2. Provision this installation's dedicated resources and review/apply migrations, including `0009_account_lifecycle.sql`. Review/apply the private owner setup SQL to that database. It fails if any user exists. It never creates an active owner or promotes an existing account. Do not use the legacy `owner` command for new email/password installations.
3. Complete Cloudflare Email Service sender-domain onboarding for `tryvitris.com` in the deployment account. Verify `accounts@tryvitris.com` is an approved sender. Keep the `AUTH_EMAIL` binding restricted with `allowed_sender_addresses: ["accounts@tryvitris.com"]`; recipient restrictions must permit the intended recipients. Changing a sender requires an explicit configuration review. Follow [Cloudflare's send binding documentation](https://developers.cloudflare.com/email-service/configuration/send-bindings/).
4. Install `PASSWORD_PEPPER` as a strong random installation secret of at least 32 characters. **Preserve the existing value on upgrades.** Install a separate `AUTH_EMAIL_ENCRYPTION_KEY` secret consisting of 32 random bytes encoded as 64 hexadecimal characters. Never commit either value, write them to public setup artifacts, or print credentials in agent output. Use Wrangler's secret input prompts or secret stdin for the intended Worker/environment.
5. Enable `PASSWORD_LOGIN=1`, `AUTH_ACCOUNTS_ENABLED=1`, `AUTH_FROM=accounts@tryvitris.com`, and finally `AUTH_EMAIL_READY=1` after the sender and bindings are verified. New scaffolds keep readiness at `0`. Preserve the returned `scheduled` handler and a one-minute cron for queued mail. Workers can also drain mail through `ExecutionContext.waitUntil` after account requests. A wrapper must forward the execution context or provide the cron. Existing Cloudflare Pages installations need a separately reviewed Worker/scheduler strategy; Pages does not run Worker cron triggers. Never redeploy an installation as another platform implicitly.
6. The designated owner opens `https://ADMIN_HOST/account/setup` and requests the email. No other address can claim the first owner. The email link lasts 24 hours. Opening a link only displays the form; the owner explicitly chooses and confirms a password of at least 15 characters. They then sign in normally. Do not send a customer's initial setup email without authorization.

## Existing installations and teams

Back up D1 before migration. Existing users, legacy password verifiers, sessions, roles, website forms and connection grants are preserved by migration 0009. Do not designate a new first owner or regenerate `PASSWORD_PEPPER`. After an authorized rollout, an existing owner signs in normally, opens **Account security**, and requests email verification. Verification lasts 30 minutes and needs an explicit confirmation. Refresh verification status after confirming in another tab.

A verified owner can invite administrators, editors and analysts under **Users & access**, after entering their current password. Ownership transfer is outside this flow. Existing active or disabled accounts cannot be reinvited or silently reactivated. Invitations last 24 hours. Cancel revokes the link; resend requires a fresh password check and replaces the previous link. Acceptance verifies the invited email and creates the assigned account atomically. A later issuer role change, deactivation or email change revokes pending invitations. Only owners can manage invitations; administrators can view users. All signed-in roles can reach their own Account security.

Forgot-password requests always return the same response for known and unknown emails. A reset link lasts 30 minutes and works once. Completion verifies access to the email, changes the password, invalidates existing sessions and old login links, and queues a password-change notice. It never signs the user in automatically. The newest requested link replaces older links. Account identity/role changes also invalidate pending actions and sessions. The lifecycle setting disables the old magic-link sign-in routes; existing password sign-in remains available when account email is not ready.

Tokens are random 256-bit values. Action tables retain only SHA-256 digests scoped to the exact installation, origin, recipient, purpose and credential revision. Completion guards and D1 triggers apply user creation/verification/password changes/session revocation/audit in one transaction. Link fragments are removed from browser history on startup, never echoed in the UI, and not sent by GET requests. Passwords retain the existing PBKDF2-SHA256 plus installation HMAC pepper format (100,000 iterations, 1,536-bit output); legacy 256-bit output remains supported. This respects [Cloudflare's production PBKDF2 limit](https://github.com/cloudflare/workerd/issues/1346). It does not claim equivalence to OWASP's 600,000-iteration configuration.

## Delivery, recovery and rollout

Mail bodies containing links are AES-GCM encrypted in the installation outbox with scope/job authenticated data. A lease permits one sender to claim each job. `sent` / **Email submitted** means provider acceptance, not inbox delivery. Failures and ambiguous expired leases are not automatically retried; request a new email or resend the invitation to generate a new link. Never expose queued ciphertext, raw links, passwords or provider errors through the API or logs. Local captured mail proves behavior only; real sender/inbox delivery needs a separately authorized acceptance check.

Preserve the encryption secret while pending jobs exist. For a deliberate key replacement, invalidate outstanding links and supersede pending/sending/failed jobs in this installation before changing the secret; recipients must request fresh links. Back up the database and preserve the password pepper in recovery. Disabling `AUTH_ACCOUNTS_ENABLED` stops lifecycle APIs and delivery, but does not undo passwords or users already created. Do not roll back the database to recover mail availability. Monitor outbox counts/status through trusted operator queries, never by dumping message bodies.

Before live rollout, review the package/install diff, migration backup, exact host, existing owner, email sender approval, secrets, scheduler and recovery plan. Run package checks and a packed external-install test. Then deploy only the explicitly authorized installation, verify existing password login and intended permissions, and separately authorize any real recipient mail test. This build does not migrate or enable existing installations automatically.


## Cloudflare Pages mail transport

Pages installations can import `createPagesAdmin` from `@tryvitris/website-admin-harness/pages`. Bind `AUTH_MAIL_SERVICE` to a dedicated private Worker for that installation. The Worker imports `createAccountMailWorker` from `@tryvitris/website-admin-harness/account-mail` and uses the same manifest, dedicated D1 database and per-installation mail encryption key. It does not need a copy of the password pepper. Keep `workers_dev=false`, `preview_urls=false`, and no public routes. Use a restricted native `AUTH_EMAIL` binding with `allowed_sender_addresses`; add the one-minute cron after confirming account capacity. The Pages wrapper forwards execution context so requests can dispatch queued messages through `waitUntil` as well.

For `accounts@tryvitris.com`, onboard `tryvitris.com` as the sending domain. Onboarding `accounts.tryvitris.com` creates a different sending domain and does not configure that root-domain address. Preserve existing Google Workspace MX records at the root; Email Sending bounce MX/SPF/DKIM records use `cf-bounce` separately. Compare imported service records against the original registrar export and retain their DNS-only routing during a DNS migration. Preserve an existing DMARC policy; an initial monitoring policy avoids imposing a new rejection policy on existing senders before their authentication is checked.

Sending to arbitrary owner/team addresses requires [Workers Paid](https://developers.cloudflare.com/email-service/platform/pricing/). Obtain explicit authorization for the subscription before changing billing. The shared address is configured as an outbound sender; inbound mailbox aliases remain with the existing mail provider. Do not replace root MX records with Email Routing as part of sender setup. Capture provider acceptance separately from confirmed inbox receipt, and send live tests only to an explicitly authorized recipient.
